# ДЗ 5. Наблюдаемость PredictiveGuard AI

По дашборду «Конвейер» видно, где образовалась очередь, хватает ли воркеров и сколько времени занимает обработка. Если нужно разобраться с одной задачей, её можно найти по `task_id`, открыть трейс из лога и посмотреть, где ушло время.

## Запуск

Команды выполняются из корня проекта. На чистых томах сначала нужно обучить модель. Воркер берёт из MLflow версию с alias `champion`.

```bash
test -f .env || cp .env.example .env
docker compose up -d --build --wait mlflow app-db rabbitmq
docker compose --profile training run --rm trainer
docker compose --profile observability up -d --build --wait
```

Если модель уже зарегистрирована, достаточно последней команды. Откройте [дашборд «Конвейер»](http://127.0.0.1:3000/d/pg-pipeline). Пользователь Grafana — `admin`, пароль задаётся в `GRAFANA_ADMIN_PASSWORD`.

| Команда | Что добавится к приложению |
|---|---|
| `docker compose up -d` | Только приложение и его зависимости |
| `docker compose --profile logs up -d` | Alloy и Loki |
| `docker compose --profile traces up -d` | OpenTelemetry Collector и Tempo |
| `docker compose --profile metrics up -d` | OpenTelemetry Collector и Prometheus |
| `docker compose --profile observability up -d` | Все три сигнала и Grafana |

CSV-источник запускается отдельно с профилем `batch`. Приложение работает и без Collector. Отправка телеметрии идёт в фоне, а потерянные при недоступности Collector данные не восстанавливаются из базы задач. Для разработки экспорт можно отключить через `OTEL_SDK_DISABLED=true`.

## Почему выбрали этот стек

**Логи.** Стандартного Python `logging` достаточно, чтобы собрать записи приложения и библиотек одним JSON-форматтером и писать их в stdout. Уровень задаёт `LOG_LEVEL`. Alloy читает логи контейнеров через Docker socket с монтированием только для чтения и фильтрует их по имени Compose-проекта. Для этого стенда в Loki хватает трёх индексируемых лейблов — `service`, `level` и `env`. Если индексировать UUID каждого задания, даже одна пачка из 6000 задач создаст тысячи потоков. Поэтому по `task_id` и `trace_id` ищем внутри JSON.

**Трейсы.** OpenTelemetry передаёт `traceparent` через RabbitMQ, а воркер переносит контекст в поток, где работает модель. Так в Tempo видна цепочка от HTTP-запроса до записи результата в PostgreSQL. У каждой реплики свой `service.instance.id`. Collector принимает данные по OTLP, ограничивает расход памяти и отправляет спаны в Tempo пачками. На учебном стенде `parentbased_always_on` сохраняет локальные трейсы и учитывает решение входящего родителя. Для потока в сотни задач в секунду начали бы с `parentbased_traceidratio` и доли 5%, затем подобрали бы её по объёму данных и тому, как часто нужен поиск по трейсам.

**Метрики.** API, воркеры и RabbitMQ работают постоянно, поэтому Prometheus опрашивает их. RabbitMQ отдаёт глубину очередей, неподтверждённые сообщения и RSS брокера через свой плагин на порту 15692. CSV-источник может закончить работу между двумя опросами, поэтому он отправляет метрики по OTLP через Collector, в том числе при завершении. Границы гистограммы inference рассчитаны относительно `INFERENCE_DELAY_SECONDS`. Например, при задержке 0,5 с рядом с ней есть границы 0,475, 0,5 и 0,525 с. [Документация метрик RabbitMQ](https://www.rabbitmq.com/docs/4.1/prometheus#erlang-vmdisk-io-via-rabbitmq)

## Сколько получается временных рядов

Считаем число сочетаний лейблов и умножаем на число рядов для каждого сочетания. Гистограмма inference для двух воркеров даёт до **38 рядов** по формуле 2 × (15 конечных бакетов + `+Inf` + `_sum` + `_count` + `_created`). Счётчик итогов даёт до **12 рядов** по формуле 2 воркера × 3 итога × 2 ряда (`_total` и `_created`). Для HTTP-счётчика каждое наблюдаемое сочетание маршрута, метода и статуса добавляет до двух рядов на реплику API.

RSS RabbitMQ даёт один ряд на узел. У метрик очередей число рядов растёт с числом очередей, у метрик воркеров — с числом реплик. У временных рядов Prometheus нет лейблов `task_id` и `trace_id`. Если добавить `task_id` к счётчику итогов, 6000 успешных задач создадут 6000 отдельных рядов `_total` вместо одного на воркер.


### Запросы для Explore

```logql
{service=~"pg-.+"} | json | task_id = "<task_id>"
{service=~"pg-.+"} | json | trace_id = "<trace_id>"
{service=~"pg-source|pg-worker"} | json | run_id = "<run_id>"
{service=~"pg-.+",level=~"ERROR|CRITICAL"}
```

```promql
sum(rate(pg_source_published_total[30s]))
sum(rate(pg_worker_tasks_total{result="ok"}[30s]))
sum by (instance) (rate(pg_worker_tasks_total{result="ok"}[30s]))
rabbitmq_detailed_process_resident_memory_bytes{job="rabbitmq"}
```

Панель SLO показывает долю завершённых задач с успешным результатом за 60 с. При очереди в 100 сообщений и задержке 0,5 с у одного воркера ожидание может занять около 50 с. Оставшиеся 10 с дают запас на публикацию, работу модели и запись результата. Цель стенда — 99%. Попадание в DLQ считается промахом.

## Память и хранение данных

Суммарный лимит шести контейнеров наблюдаемости — **1408 MiB**. Под нагрузкой максимальное значение из пяти замеров `docker stats` составило **831,67 MiB**. Этот бюджет относится к Alloy, Loki, Collector, Tempo, Prometheus и Grafana. RSS RabbitMQ отображается отдельно на панели **Память процессов RSS**.

Loki, Tempo и Prometheus хранят данные два дня. Версии образов закреплены, данные хранилищ лежат в именованных томах. Grafana загружает источники данных, дашборд и алерты из файлов при старте. Для проверки с нуля используйте отдельный тестовый Compose-проект, так как `down -v` удаляет данные и зарегистрированные модели этого проекта.
